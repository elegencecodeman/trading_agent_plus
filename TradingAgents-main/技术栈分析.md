## LangGraph 多智能体编排

### 有向图拓扑

`tradingagents/graph/setup.py` 中的 `GraphSetup.setup_graph()` 构建了一个 **StateGraph(AgentState)**，完整拓扑如下：

```
START
  │
  ├─→ Market Analyst ──(conditional)──→ ToolNode(market) ──→ MsgClearMarket
  │         │                                                        │
  │         └── 无 tool_calls 时 ─────────────────────────────→ MsgClearMarket
  │                                                                      │
  ├─→ Sentiment Analyst ─(conditional)─→ ToolNode(social) ──→ MsgClearSentiment
  │                                                                      │
  ├─→ News Analyst ────(conditional)──→ ToolNode(news) ────→ MsgClearNews
  │                                                                      │
  ├─→ Fundamentals Anlyst(conditional)→ ToolNode(fundamentals)→ MsgClearFundmtls
  │                                                                      │
  ├─→ Bull Researcher ←──(conditional)──→ Bear Researcher
  │        │                                    │
  │        └── count >= 2×max_debate_rounds ──→ Research Manager
  │                                                     │
  ├─→ Trader ──────────────────────────────────────────
  │                                                     │
  ├─→ Aggressive → Conservative → Neutral  (条件循环)
  │        │                                    │
  │        └── count >= 3×max_risk_discuss_rounds ──→ Portfolio Manager
  │                                                           │
  └──────────────────────────────────────────────────────────→ END
```

### 关键 LangGraph 机制

| 机制 | 实现文件 | 说明 |
|------|---------|------|
| **条件边 (Conditional Edges)** | `conditional_logic.py` | `should_continue_market()` 检查 `last_message.tool_calls` 是否存在，决定继续调工具还是进入清除节点 |
| **辩论循环** | `should_continue_debate()` | 检查 `count >= 2×max_debate_rounds`，不满足则在 Bull/Bear 间乒乓往复 |
| **风险分析循环** | `should_continue_risk_analysis()` | 检查 `count >= 3×max_risk_discuss_rounds`，不满足则在 3 方之间轮转 |
| **状态管理** | `AgentState(MessagesState)` | 融合了 LangGraph 内置的消息流 + 自定义业务字段（报告/辩论状态/交易决策） |
| **检查点续跑** | `langgraph-checkpoint-sqlite` | `SqliteSaver` 存储状态快照，通过 `thread_id` 恢复中断的执行 |
| **Graph 编译** | `workflow.compile()` | 支持带/不带 checkpointer 的动态重编译 |

### 状态定义

```python
class AgentState(MessagesState):
    company_of_interest: str          # 分析的股票代码
    asset_type: str                   # "stock" 或 "crypto"
    instrument_context: str           # 确定性身份解析（公司名/行业/交易所）
    trade_date: str                   # 交易日期

    # 分析师输出
    market_report: str                # Market Analyst 报告
    sentiment_report: str             # Sentiment Analyst 报告
    news_report: str                  # News Analyst 报告
    fundamentals_report: str          # Fundamentals Analyst 报告

    # 辩论状态
    investment_debate_state: InvestDebateState   # 多空辩论历史 + count
    investment_plan: str              # Research Manager 产生的投资计划

    # 交易与风险管理
    trader_investment_plan: str       # Trader 的交易提案
    risk_debate_state: RiskDebateState  # 风险辩论历史 + count
    final_trade_decision: str         # Portfolio Manager 最终决策
    past_context: str                 # 历史记忆注入
```

### 双 LLM 模型策略

| 模型级别 | 配置键 | 使用节点 | 原因 |
|---------|--------|---------|------|
| **Deep Thinking** | `deep_think_llm` | Research Manager, Portfolio Manager | 需要深度推理、综合多维度信息 |
| **Quick Thinking** | `quick_think_llm` | 所有其他 9 个节点 | 数据查询、单维度分析、格式化输出 |

## 多供应商 LLM 工厂

### 架构：工厂 + 策略 + 注册表

```
create_llm_client(provider, model, base_url, **kwargs)
        │
        ▼
    factory.py ─── 路由判断
        │
        ├─ "anthropic"         → AnthropicClient      → ChatAnthropic
        ├─ "google"            → GoogleClient          → ChatGoogleGenerativeAI
        ├─ "azure"             → AzureOpenAIClient     → AzureChatOpenAI
        ├─ "bedrock"           → BedrockClient         → ChatBedrock
        └─ 其他 14 个           → OpenAIClient          → NormalizedChatOpenAI
           (openai/xai/deepseek/qwen/glm/minimax/      │
            openrouter/mistral/kimi/groq/nvidia/       ├─ DeepSeekChatOpenAI
            ollama/openai_compatible)                   ├─ MinimaxChatOpenAI
                                                       └─ LocalCompatibleChatOpenAI
```

### 三个关键抽象

| 层 | 文件 | 解决什么问题 |
|----|------|-------------|
| **ModelCapabilities** | `capabilities.py` | 声明每个模型支持什么 API 参数：`tool_choice`？`json_schema`？`reasoning_content` 回传？用一个 dataclass 统一建模 |
| **ProviderSpec** | `openai_client.py` | 声明每个供应商的特性：`base_url`、`chat_class`、`key_optional`、是否走 Responses API。一个 dataclass 替代零散的 if/else |
| **NormalizedChatOpenAI** | `openai_client.py` | 统一处理内容格式差异（Responses API 返回 list 块，Chat API 返回 string），根据 capabilities 自动选择 structured_output 的方法 |

### 能力表（示例）

```python
# DeepSeek thinking 模型：支持 tools 数组，但不允许 tool_choice 参数
_DEEPSEEK_THINKING = ModelCapabilities(
    supports_tool_choice=False,       # → langchain 不传 tool_choice kwarg
    supports_json_mode=True,
    supports_json_schema=False,
    preferred_structured_method="function_calling",  # 绑 schema 为 tool
    requires_reasoning_content_roundtrip=True,       # → DeepSeekChatOpenAI 自动回传
)
```

### DeepSeek 特殊处理

`DeepSeekChatOpenAI` 子类在 NormalizedChatOpenAI 之上处理两个 DeepSeek 特有行为：

1. **reasoning_content 回传** — DeepSeek thinking 模型返回 `reasoning_content` 后，下一轮请求必须原样回传，否则 API 返回 HTTP 400
2. **tool_choice 抑制** — V4 和 reasoner 模型接受 `tools` 数组但拒绝 `tool_choice` 参数，通过 capabilities 声明后自动处理

### MiniMax 特殊处理

`MinimaxChatOpenAI` 子类处理 M2.x 推理模型：

- M2.x 默认把 `<think>` 块嵌入 `content` 中，通过 `reasoning_split=True`（经 `extra_body` 传递）重定向到 `reasoning_details`
- `requires_reasoning_split` 被 capabilities 门控，非推理模型不会收到此参数

## 结构化输出机制

三个决策智能体使用 **Pydantic Schema + Structured Output**：

```
Pydantic Model                      Agent
─────────────────────────────       ──────────────────
ResearchPlan                        Research Manager  (deep thinking LLM)
  ├─ rating: PortfolioRating
  ├─ rationale: str
  └─ strategic_actions: list[str]

TraderProposal                      Trader            (quick thinking LLM)
  ├─ action: TraderAction
  ├─ entry_price: Optional[float]
  ├─ stop_loss: Optional[float]
  └─ position_sizing: str

PortfolioDecision                   Portfolio Manager (deep thinking LLM)
  ├─ rating: PortfolioRating
  ├─ executive_summary: str
  ├─ investment_thesis: str
  ├─ price_target: Optional[float]
  └─ time_horizon: str

SentimentReport                     Sentiment Analyst  (quick thinking LLM)
  ├─ overall_band: str
  ├─ overall_score: int
  ├─ confidence: str
  └─ narrative: str
```

### 多供应商适配策略

`tradingagents/agents/utils/structured.py` 中的 `bind_structured()` + `invoke_structured_or_freetext()`：

```
bind_structured(llm, Schema)
  │
  ├─ 成功 → with_structured_output(Schema) 包装 → invoke → Pydantic 实例 → render() → Markdown
  │
  ├─ 返回 None (供应商不支持) → 直接 llm.invoke() → 自由文本
  │
  └─ invoke 失败 (JSON 解析错误等) → 重试一次 → llm.invoke() → 自由文本
```

### 各供应商 Structured Output 实现对照

| 供应商 | 方法 | 底层实现 |
|--------|------|---------|
| OpenAI | `json_schema` | `response_format={"type":"json_schema","schema":...}` |
| xAI | `json_schema` | 同 OpenAI |
| DeepSeek | `function_calling` | 绑 Pydantic 为 tool，但不传 `tool_choice` 参数 |
| Gemini | `json_schema` | 使用 `response_schema` 参数 |
| Anthropic | `function_calling` | 绑 Pydantic 为 tool use，遵循 Anthropic tool-use 协议 |
| Ollama | 回退到 `none` | `preferred_structured_method=none` → 自由文本生成 |

### 工具注册

```
@tool 装饰器                           LangGraph ToolNode
─────────────────────                  ────────────────────
prediction_markets_tools.py  ─────→    ToolNode(news)
news_data_tools.py          ─────→       ├─ get_news
core_stock_tools.py         ─────→       ├─ get_global_news
technical_indicators_tools.py ─────→     ├─ get_macro_indicators
fundamental_data_tools.py   ─────→       └─ get_prediction_markets
macro_data_tools.py         ─────→
                              ─────→    ToolNode(market)
                              ─────→      ├─ get_stock_data
                              ─────→      ├─ get_indicators
                              ─────→      └─ get_verified_market_snapshot

                              ─────→    ToolNode(fundamentals)
                              ─────→      ├─ get_fundamentals
                              ─────→      ├─ get_balance_sheet
                              ─────→      ├─ get_cashflow
                              ─────→      └─ get_income_statement
```

### 工具调用完整数据流

```
LLM 输出 tool_calls: [{name: "get_prediction_markets", args: {topic: "Fed rate cut"}}]
  │
  ▼
LangGraph 拦截 tool_call → 找到对应的 ToolNode("news")
  │
  ▼
@tool 包装函数: prediction_markets_tools.get_prediction_markets("Fed rate cut", 6)
  │
  ▼
interface.route_to_vendor("get_prediction_markets", "Fed rate cut", 6)
  │
  ▼
查 TOOLS_CATEGORIES → 类别 "prediction_markets"
查 get_vendor() → 供应商链 ["polymarket"]
查 VENDOR_METHODS → 找到 polymarket.get_prediction_markets
  │
  ▼
polymarket.get_prediction_markets("Fed rate cut", 6)
  → HTTP GET https://gamma-api.polymarket.com/public-search?q=Fed+rate+cut
  → 返回 Markdown 字符串
  │
  ▼
结果挂回 LLM 消息上下文 → LLM 据此续写分析报告
```

### @tool 装饰器中的 Annotated 类型标注

```python
@tool
def get_prediction_markets(
    topic: Annotated[str, "Event topic/keyword, e.g. 'Fed rate cut', 'recession 2026'..."],
    limit: Annotated[int | None, "Max markets to return; omit for a default of 6"] = None,
) -> str:
    """Retrieve live, market-implied probabilities from prediction markets..."""
    return route_to_vendor("get_prediction_markets", topic, limit)
```

**作用**：`Annotated[str, "..."]` 中的描述被 LangChain **自动转换为 LLM function-calling 的 JSON Schema**，LLM 靠这些描述来准确理解每个参数的含义和格式。

## 数据供应商路由层

### 供应商注册

`tradingagents/dataflows/interface.py` 是整个数据系统的调度中心：

```
                    ┌──────────────────────┐
   LLM 调用工具      │    interface.py      │
                    │                      │
   "我要股价"  ────→ │  TOOLS_CATEGORIES     │  ← 工具→类别目录
                    │        ↓             │
                    │  get_vendor()        │  ← 配置解析 (类别级 + 工具级)
                    │        ↓             │
                    │  VENDOR_METHODS       │  ← 方法→供应商→函数 二维表
                    │        ↓             │
                    │  route_to_vendor()   │  ← 运行时调度 + 回退 + 容错
                    │        ↓             │
                    │  具体供应商函数        │
                    └──────────────────────┘
```

### 三种异常 → 三种路由行为

| 异常 | 路由行为 | 场景示例 |
|------|---------|---------|
| `VendorNotConfiguredError` | 跳过此供应商，换下一个 | FRED API Key 未配置 |
| `VendorRateLimitError` | 被限流，换下一个 | Alpha Vantage 免费额度用完 |
| `NoMarketDataError` | 记录 symbol + detail，跳过 | 股票代码不存在或已退市 |

### 核心数据 vs 可选数据

```python
OPTIONAL_CATEGORIES = {"macro_data", "prediction_markets"}
```

| 核心数据（失败 → 崩溃） | 可选数据（失败 → 降级提示） |
|------------------------|--------------------------|
| OHLCV 股价、技术指标、财务报表、新闻 | 宏观指标（FRED）、预测市场（Polymarket） |

## 记忆与反思系统

### 三步走架构

```
Phase A: 运行时存储 (同步)
─────────────────────────────
Portfolio Manager 决策
  → signal_processor.process_signal()     # 从 Markdown 提取 Rating
  → memory_log.store_decision()           # 写入 trading_memory.md
     格式: [2024-05-10 | NVDA | Buy | pending]
     内容: DECISION: (完整 Markdown 决策文本)
     ← 标记 pending (尚未验证)

Phase B: 下次运行时反思 (异步)
─────────────────────────────
下次运行同一 ticker:
  → _resolve_pending_entries()
  → _fetch_returns()                      # yfinance 拉取实际收益
  → reflector.reflect_on_final_decision()  # LLM 分析对错
     输出: "The directional call was correct (+3.2% alpha).
            The thesis held because... One lesson: ..."
  → 更新标记: [2024-05-10 | NVDA | Buy | resolved | +3.2%]

Phase C: 上下文注入
─────────────────────────────
  → get_past_context("NVDA", n_same=5, n_cross=3)
  → 注入 Portfolio Manager 的 prompt
     最相关: 同 ticker 最近 5 次决策 + 跨 ticker 最近 3 次教训
```

### 反思 Prompt 设计

```python
# reflection.py: _get_log_reflection_prompt()
"Write exactly 2-4 sentences of plain prose (no bullets, no headers).
 Cover in order:
 1. Was the directional call correct? (cite the alpha figure)
 2. Which part of the investment thesis held or failed?
 3. One concrete lesson to apply to the next similar analysis."
```

**设计要点**：LLM 在已知实际收益的情况下审视自己的历史决策，生成精炼的教训文本（2-4 句，无格式化），保证再次注入 Prompt 时不会膨胀上下文窗口。

## 容错与回退策略

| 层次 | 机制 | 说明 |
|------|------|------|
| **LLM 层** | 结构化输出回退 | `invoke_structured_or_freetext()` → 结构化失败自动重试一次自由文本 |
| **LLM 层** | SDK 重试预算 | `llm_max_retries` 配置跨供应商的 429 限流自动重试 |
| **供应商层** | 多供应商回退链 | `data_vendors="yfinance,alpha_vantage"` 逗号分隔有序回退 |
| **供应商层** | 可选数据降级 | `OPTIONAL_CATEGORIES` 中的类别失败不崩溃，返回 `DATA_UNAVAILABLE` |
| **供应商层** | 无数据标记 | `NO_DATA_AVAILABLE` 明确告诉 LLM "不要编造数据" |
| **网络层** | 超时保护 | 所有 HTTP 请求设 30 秒超时 |
| **编排层** | 检查点续跑 | LangGraph checkpoint → 崩溃后从上一个成功节点恢复 |
| **数据层** | 日期安全 | 所有数据源过滤 `endDate > curr_date` 的行，防止前视偏差 |
| **数据层** | OHLCV 保鲜 | 最新行超过 10 天未更新的缓存数据被拒绝 |
| **身份层** | 防幻觉 | 启动时确定性地用 yfinance 解析公司真实身份，注入所有 Agent |

```
    │能力声明表│           │失败回退自由文本│          │LLM反思   │
    │双模型分级│           │              │          │历史注入  │
    └──────────┘           └──────────────┘          └──────────┘
```

### 核心技术选型理由

| 技术选型 | 理由 |
|---------|------|
| **LangGraph 而非 LangChain AgentExecutor** | 需要精确控制节点顺序、条件循环和辩论回合数，而非让 LLM 自主决定执行路径 |
| **工厂模式 LLM 客户端** | 支持 16+ 供应商，每个有不同的 API 参数约束和结构化输出方式，必须统一抽象 |
| **能力声明表 (ModelCapabilities)** | 每个模型对 `tool_choice`/`json_schema`/`reasoning_content` 的支持不同，声明式配置避免 if/else 地狱 |
| **双 LLM 模型分级** | 复杂推理节点（Research Manager、Portfolio Manager）用强模型，数据查询节点用快模型，平衡质量与成本 |
| **数据预注入 (Sentiment Analyst)** | 避免 LLM 在 prompt 压力下虚构 Reddit/X 内容（已实际验证过的 hallucination 问题，issue #557） |
| **可选/核心数据分离** | FRED 和 Polymarket 的不可用不应阻止整个分析流水线，降级而非崩溃 |
| **CHECKPOINT 续跑** | 一次完整运行可能涉及 20+ LLM 调用和多次网络请求，长时间运行需要故障恢复 |
| **记忆系统为追加日志而非向量数据库** | 结构化程度高的金融决策更适合精确匹配（同 ticker 历史），而非语义检索 |
